## 1. What JROS Is

**JROS = "Jewellery Relationship Operating System"** — a white-label, multi-tenant SaaS platform letting jewellers (tenants) run digital gold-savings schemes under their own brand. Business model: JROS → Jeweller (tenant) → Consumer. JROS never touches physical gold or sells directly to consumers.

Full requirements source: `docs/jros-product-bible_3.html` (24-chapter formal spec) and `docs/jros-interactive-prototype 1.html` (click-through mockup), both under `docs/` at the project root (moved there in §15's repository cleanup). These are the ground truth for business rules not otherwise specified.

## 2. Tech Stack

- **Backend**: FastAPI, SQLAlchemy 2.0 (async), Alembic, Pydantic v2, Repository Pattern + Service Layer, JWT auth with refresh-token rotation, RBAC, multi-tenant (shared schema, `tenant_id` on every table).
- **Database**: **Live Supabase Postgres** (`aws-0-ap-northeast-1.pooler.supabase.com`) — NOT local, no Docker, no SQLite. Connection string in `Backend/.env`. (A leftover unused `Backend/jros_dev.db` SQLite file existed early on — it was deleted in §15's repository cleanup; there is no local DB file anywhere in this project.)
- **Frontend**: Next.js (App Router) + TypeScript. Customer app renders inside a fixed mobile-frame shell (`src/app/customer/layout.tsx`); Admin/SuperAdmin use a full dashboard sidebar shell.
- **Servers**: Both run locally — backend on port 8000 (`uvicorn app.main:app --reload`), frontend on port 3000 (`npm run dev`). Both were running throughout this session. **The backend crashed once** (unrelated resource issue after ~5hrs, not a code bug) and was restarted identically — if it's down again, just restart it the same way.

## 4. Critical Architecture Rules — Follow These Exactly For New Modules

1. **Tenant isolation everywhere**: every service method checks `if not current_user.tenant_id: raise ForbiddenException(...)` first. Every repository query filters by `tenant_id`. SuperAdmin has `tenant_id = None` and is structurally blocked from tenant data this way — no special-casing needed for reads, but **admin write endpoints use `require_admin_only`** (not `require_admin`, which wrongly includes SuperAdmin) to explicitly exclude SuperAdmin per business rules.
2. **Own-only access for customers**: never leak resource existence — return `404 ResourceNotFoundException`, never `403`, when a customer requests something that exists but isn't theirs (or belongs to another tenant). Established via `EnrollmentRepository.get_enrollment_by_id_for_customer`-style methods.
3. **Response envelope**: `StandardSuccessResponse{success, message, data, meta}` on success; `{success:false, message, errors:[{code,message,field?}]}` on error (via `app/exceptions/base.py` exception classes: `ValidationException`, `UnauthorizedException`, `ForbiddenException`, `ResourceNotFoundException`, `ConflictException`).
4. **Admin responses include derived names** (e.g. `customer_name`, `scheme_name`) via eager-loaded relationships (`selectinload`), constructed manually in the service (not `.model_validate()`) since these aren't direct model columns. **Customer responses are lean** — no `tenant_id`, no internal actor IDs, no gateway metadata.
5. **Audit logging**: only on WRITE operations (`AuditRepository.create_log(...)`), never on GET/read endpoints — this is consistent everywhere, don't add it to read-only routes.
6. **Money fields**: plain `Float` columns (not `Decimal`), matching existing convention.
7. **Closed enums** (payment_status, payment_method, etc.): Pydantic v2 `Literal[...]` types in request schemas — clean automatic validation errors, no custom validators needed.
8. **Soft delete**: reuse an `is_active` boolean flag (see `Scheme.is_active`), not a dedicated `deleted_at` column — no such pattern exists elsewhere in this codebase.
9. **"Today" must use IST**, not UTC — this is an India-only business. Use the fixed-offset helper pattern from `goldrate_service.py` (`IST = timezone(timedelta(hours=5, minutes=30))`) — no `tzdata` package needed since IST has no DST.
10. **Don't invent business rules**: GST/fees/taxes/discounts/EMI/wallets are explicitly undefined — don't assume them. When something is ambiguous, build the extension point and document it, don't guess.
11. **Frontend service files**: one per backend module (`goldRateService.ts`, `schemeService.ts`, etc.), each defining its own lean TypeScript types (not reusing the old pre-existing `src/types/index.ts` mock-era types, which have incompatible field names/shapes from the original prototype mock data).
12. **Reuse existing mock UI layouts** wherever the user has asked for it — check `src/mock/mockData.ts` and existing pages before building new ones from scratch. This has been an explicit, repeated instruction.

## 9. Style/Process Notes From This Session

- The user frequently asks "how much time" during long pytest runs — compute an honest ETA from elapsed-time ÷ progress-percentage (grep the `[ XX%]` markers + timestamps from the log), don't guess.
- When a background test run seems stuck, verify via `Get-Process -Id <pid> | Select CPU` twice a few seconds apart — near-zero CPU delta means it's hung (kill and retry), advancing CPU means it's just slow (let it finish).
- The user has explicitly told me to stop a running regression mid-flight before (`Module 8`) — always confirm before running large test suites if there's any ambiguity, and respect "only run what's important."
- Always disclose scope/interpretation decisions clearly in reports rather than silently guessing (e.g., the Module 6 admin-vs-SuperAdmin authorization ambiguity was flagged explicitly).
- Reports follow a consistent format per module: Files created/modified, DB changes, APIs added, Tests executed/results, Bugs found, Final Status (🟢/🟡/🔴), plus whatever extra sections a given module's instructions asked for (e.g. "Regression Status: deferred").
- **⚠️ Never run `npm run build` (or anything that does `rm -rf .next`) while `npm run dev` is running on port 3000.** Discovered right after Module 18: `next build` deletes `.next` before rebuilding; if a live `next dev` process still has that directory's old webpack chunks cached in memory, subsequent page requests fail with `Cannot find module './XXXX.js'` (a corrupted webpack-runtime reference), returning a 500 on every route. This happened after this session ran `tsc`/`next build` verification steps repeatedly across Modules 16–18 while an earlier `npm run dev` instance (port 3000) was still up from much earlier in the session. **Fix**: stop the `next dev` process (`Get-NetTCPConnection -LocalPort 3000` → `Stop-Process -Id <pid> -Force`), delete `.next` again now that nothing has it open, then restart `npm run dev`. Not a code bug — don't go looking for one if you see this error, just restart the dev server. Unlike the port-8000 anomaly below, port 3000's process is always visible to normal Windows tooling in this environment.
- **⚠️ Port 8000 may be held by a process invisible to this machine's normal Windows tooling.** During Module 12, `Get-Process`, `Stop-Process`, and even `taskkill /PID` all reported "process not found" for the PID that `Get-NetTCPConnection -LocalPort 8000` said owned the socket — yet that PID was actively answering real HTTP requests with stale (pre-Module-12) code. Very likely a WSL2-hosted `uvicorn` instance (WSL2's localhost port-forwarding can present sockets under PIDs the Windows process table can't resolve) watching the same files via the Windows-mounted path, whose file-watcher is unreliable — consistent with Module 11's note that `--reload` didn't pick up changes either. **If a freshly-added route 404s after you've confirmed the code and router registration are correct** (verify with `python -c "from app.api.v1.router import api_router; ..."` — this direct import is reliable even when the HTTP server isn't), don't sink time into repeatedly killing/restarting Windows-visible processes on port 8000 — it may not be reachable from this session. Fall back to the pytest suite (which exercises the real `app.main.app` object in-process via `httpx.ASGITransport`, completely bypassing whatever is bound to port 8000) as the authoritative check, and flag the port-8000 anomaly to the user so they can restart it from wherever they actually run it (check for a WSL terminal).

## 20. Module 18 — Authentication Hardening (2026-07-29)

**What was built**: Forgot Password, Reset Password, and Email Verification, all built on top of the existing JWT/RefreshToken authentication architecture — no redesign of login/signup/refresh/logout. Secure, single-use, expiring tokens (mirroring `RefreshToken`'s exact hash-at-rest pattern). A real, working email-provider abstraction (`ConsoleEmailProvider` active by default, `SMTPEmailProvider` ready once configured) so the whole flow is genuinely testable end-to-end today, with zero real email infrastructure required.

### Architecture decisions
- **Reused the existing "no repository layer for Auth" convention.** Every other module in this codebase has a Repository + Service split; `auth_service.py` never did (it always queried `User`/`RefreshToken` directly via `select()`). Rather than introduce a repository layer just for this module — which would make Auth *less* internally consistent, not more — the new methods extend `AuthService` directly, matching Auth's own established style exactly, per this module's explicit "reuse existing authentication architecture" instruction.
- **One shared `TokenService`, two separate token tables.** `app/services/token_service.py` centralizes the only genuinely-shared logic between password reset and email verification: generating a 256-bit URL-safe raw token (`secrets.token_urlsafe(32)`, stdlib, no new dependency) and hashing it (reuses the existing `hash_token_sha256` helper `RefreshToken` already relies on). Storage stays as two separate tables, `PasswordResetToken` and `EmailVerificationToken` — this codebase's established convention is one table per concern (see `RefreshToken` vs. `KYCRecord` vs. `AuditLog`, never a polymorphic multi-purpose table), so that convention was kept rather than introduced a `purpose`-column design that would be a first for this codebase.
- **`used_at: Optional[datetime]`, not a boolean flag**, on both new token tables — same "value not just flag" precedent as `KYCRecord.verified_at` (Module 11): NULL means unused, a timestamp means used (and records *when*), which is strictly more useful for an audit trail than a bare `is_used: bool` at zero extra cost.
- **Email provider abstraction mirrors `payment_gateway.py`'s established "extension point" pattern — with one deliberate difference.** `payment_gateway.py` is a pure `NotImplementedError` stub; here, `ConsoleEmailProvider` is a fully working default (it logs the email rather than raising), because the task required the reset/verification *flows themselves* to be real and testable, not just scaffolded. `SMTPEmailProvider` is a genuine, working `smtplib`-based implementation (stdlib only, no new dependency) that activates automatically the moment `SMTP_HOST` is set in `.env` — "plug in SMTP" means configuring settings, not writing more code.
- **Signup now best-effort-fires a verification email** (`register_customer` calls `request_email_verification` right before returning). This is the one place existing behavior was extended rather than purely additive — justified because "email verification infrastructure" that never actually triggers on the one occasion it matters (signup) would be dead infrastructure. Wrapped in try/except, exactly mirroring the pre-existing "a failed revoke must never trap the user in a signed-in shell" resilience pattern from `logout_user` — an email-send failure can never fail signup itself.
- **Verification is infrastructure, not enforcement.** Email verification does not gate login, signup, or any existing route — `get_current_user`/`require_*` dependencies are unchanged. Gating access on verification would be an authentication *redesign*, explicitly out of scope; this module only builds the capability.
- **Password reset scope is email-only.** `User.phone`-only accounts have no reset path in this module — building SMS-based reset would need a notification/SMS provider, explicitly out of scope ("Do not implement notifications"). Flagging this as a real gap for phone-only accounts, not an oversight.

### Security considerations
- **Raw tokens are never persisted anywhere** — only their SHA256 hash, identical to how `RefreshToken` already handles its token string. The raw value exists only in the outbound email link.
- **Token expiry**: password reset tokens expire in 30 minutes (`PASSWORD_RESET_TOKEN_EXPIRE_MINUTES`); email verification tokens in 24 hours (`EMAIL_VERIFICATION_TOKEN_EXPIRE_HOURS`) — deliberately much shorter for the reset flow, since that token grants an account-takeover-adjacent action, while verification only confirms an address.
- **One-time use enforced at the row level** (`used_at`), checked before honoring any token — confirmed by tests that reuse of an already-used token of either kind is rejected even when it hasn't expired.
- **Account enumeration is explicitly prevented on `/auth/forgot-password`**: the endpoint returns the exact same response — same status code, same message — whether or not the submitted email matches a real account. `AuthService.forgot_password` silently no-ops for unknown or inactive-user emails rather than raising, and the frontend's toast message was written to be equally generic. Confirmed by a dedicated test (`test_returns_identical_200_for_unknown_email`).
- **A successful password reset revokes every existing session** (bulk-updates all of that user's `RefreshToken` rows to `is_revoked=True`) and **invalidates every other outstanding reset token** for the same user — reusing the exact bulk-revoke query pattern `logout_user`'s `all_devices` branch already established, not a new mechanism. This means if an attacker requested a reset link before the legitimate user did, completing the legitimate reset locks the attacker's link out too.
- **Every write is audit-logged** (`PASSWORD_RESET_REQUESTED`, `PASSWORD_RESET_COMPLETED`, `EMAIL_VERIFICATION_REQUESTED`, `EMAIL_VERIFIED`), reusing the existing `AuditRepository.create_log` call convention — no new audit infrastructure.
- **Known gap, flagged rather than silently addressed**: there is still no rate limiting anywhere in this codebase (confirmed absent in the Integration Audit, §17). `/auth/forgot-password` and the email-verification-request endpoint are classic abuse targets (mail-bombing a victim's inbox, or brute-forcing a token given enough attempts) without it. Adding rate-limiting middleware (e.g. `slowapi`) would be a new dependency and a broader architectural addition beyond this module's explicit scope ("reuse existing architecture") — **recommended as a follow-up before production**, not built here.
- **`SMTP_PASSWORD` will be a new secret once real SMTP is configured** — same handling as every other secret in this codebase (`.env`, gitignored, never committed) — no new secret-handling pattern was needed.

## 23. Phase A — Jewellery Catalogue & Marketing Studio: Real, Local Image Editor (2026-08-03)

**What was built**: A genuinely offline image-editing engine — crop, rotate, flip, brightness, contrast, saturation, sharpness, blur, white balance, and noise reduction, plus background replacement (white/black/luxury-blue/gradient/transparent/custom-color) — using only Pillow and OpenCV, with **zero third-party AI service of any kind**. Extends Modules 20/21's `Product`/`ProductImage` models and `StorageProvider` abstraction — nothing in either module was changed.

### Architecture decision: an ephemeral editing session, not per-adjustment persistence
Per an explicit architecture refinement, the flow is **Original Image → Editing Session (client-held, ephemeral) → Preview (rendered on demand, never persisted) → Save (persisted exactly once)**. Every intermediate adjustment — and every Preview call — writes nothing to the DB or to storage; only an explicit Save creates a new row. This is the same "insert-only, never overwrite" philosophy `ProductImage` already established for uploads, just gated behind an explicit user action instead of firing on every keystroke. Undo/redo/reset/duplicate are frontend-only concerns against this same operations list — the backend has no concept of an "editing session" as persisted state.

### Backend — new files
- `app/services/image_processing_service.py` — pure functions (no DB/storage dependency): `apply_operations(image_bytes, operations) -> (output_bytes, content_type, width, height)`. Each operation (`CROP`, `ROTATE`, `FLIP`, `BRIGHTNESS`, `CONTRAST`, `SATURATION`, `SHARPNESS`, `BLUR`, `WHITE_BALANCE`, `NOISE_REDUCTION`, `BACKGROUND_REPLACE`) is an independently-testable handler. Clean on plain-backdrop jewellery product photography (this feature's actual target); softer/imprecise on busy or reflective backgrounds. Disclosed as a known limitation, not silently overpromised — confirmed with the user before building.
  - White balance uses the gray-world algorithm; noise reduction uses OpenCV's `fastNlMeansDenoisingColored`. Both are classical, deterministic algorithms — no ML model involved anywhere in this file.

### One real bug found and fixed via testing

Caught by `test_background_replace_transparent_via_endpoint` (API-layer test, using a real but low-contrast test JPEG). Fixed by making the center-block anchor **unconditional** — jewellery product photography reliably centers the subject, so this is a safe assumption, and it guarantees GrabCut always has at least one foreground sample to work from.

## 24. Phase B — Design Studio & Rendering Engine (2026-08-03)

**What was built**: A generic, layered canvas document format (not a fixed per-template schema), a versioned `CatalogueDesign` model (insert-only — every Save is a new immutable version), one shared rendering pipeline that composites 8 layer types (Background, Product, Text, Logo, Badge, QR, Overlay, Shape) into a final image, 10 real preset templates, 9 real output-size presets, synchronous batch rendering across multiple products, and multi-product catalogue PDF generation via ReportLab. Extends Phase A + Modules 20/21 — the Image Editor, the AI-provider stub, `Product`/`ProductImage`, and `StorageProvider` are all untouched.

### Architecture decisions (per explicit refinements agreed before/during this phase)
1. **The canvas is a generic layered document, not hardcoded per template.** Every `CanvasLayer` carries the same common fields (`id`, `type`, `x`, `y`, `width`, `height`, `rotation`, `scale`, `opacity`, `visible`, `locked`, `z_index`) regardless of which of the 8 types it is; only the fields relevant to that type are read at render time (same "one flexible shape, not a discriminated union" convention `ImageEditOperation` already established in Phase A). A `props: Dict[str, Any]` catch-all on every layer means a future module can introduce a new layer type or a new per-type field without a schema migration — mirrors `ProductImage.variant_type`'s own "plain string, not a closed DB enum" extensibility precedent.
2. **`CatalogueDesign.canvas_json` stores the full layered document verbatim — nothing is flattened until render time.** Product, Text, Badge, QR, Logo, and Overlay layers stay fully independent and re-editable in storage; only `catalogue_render_service.render_canvas()`'s own output (a one-way, one-time flattening into a final JPEG) ever merges them into pixels. Reopening a saved design months later means loading `canvas_json` back into an editable layer list — nothing was ever baked in at save time. Stored as a plain `Text` column with manual `model_dump_json()`/`model_validate_json()` (de)serialization at the repository/service boundary, matching this codebase's existing `AuditLog.before_state`/`after_state` convention rather than introducing SQLAlchemy's native JSON/JSONB column type as a first for this codebase.
3. **Versioning is insert-only, exactly like `ProductImage`.** `CatalogueDesign` has no update route. Every `POST .../designs` call inserts a new row with the next `version` number (1, 2, 3... per product). Listing every row for a product, newest first, **is** the version history — no separate history table. **Restore** and **Duplicate** both just insert another new version cloned from an existing row's `canvas_json` (via a shared `_clone_design()` helper) rather than mutating anything — `source_design_id` is a self-referential FK (same lineage pattern as `ProductImage.source_image_id`) recording which version a clone came from. Restoring an old version brings it back as the *newest* version; the row it was restored from is never touched.
4. **Badges and decorative overlays are programmatic, not static PNG assets.** A badge or overlay layer can be placed at any size a design specifies — a pre-rendered raster asset would either blur when scaled up or need a whole set of pre-baked resolutions. Instead, `catalogue_asset_library.py` holds the reusable, shared part (colors/labels/keys), and `catalogue_render_service.py` draws each one fresh at render time (rounded-rect + text for badges; line/arc/rect primitives for borders, frames, corner flourishes, and a seeded-random sparkle scatter). This is the "reusable asset library" this phase's brief asked for, just expressed as resolution-independent drawing routines instead of files. The "Powered by DFX Solution" watermark is one of these overlay keys (`DFX_WATERMARK`) — there is no separate Watermark layer *type*, per the 8 types this phase defines.
5. **Fonts are the one genuinely bundled static asset** — three curated OFL-licensed families vendored under `app/assets/fonts/` (Playfair Display for serif/luxury, Poppins for clean sans-serif, Great Vibes for script/festive), sourced once from Google Fonts' repository at development time (not fetched at request time — the running app never makes a network call for typography). `NOTICE.txt` alongside them documents provenance and license. Playfair Display ships as its variable-weight file; `resolve_font()` sets the weight axis for bold with a best-effort fallback (some FreeType builds lack variable-font support) rather than requiring a second static file.
6. **A template is product-agnostic by design.** Each of the 10 `TEMPLATE_PRESETS` is a real `CanvasDocument`, but its `PRODUCT`-type layer(s) carry `image_id=None` on purpose. `CatalogueService._resolve_product_layers()` fills that in with whichever product is actually being rendered, per call — the template document itself is never mutated in storage. This is what makes **Batch Rendering** (one template, many products) and **Output Presets** (one canvas, many target sizes via `_rescale_canvas()`'s proportional layer remap) both reuse the exact same `render_canvas()` pipeline with zero duplicated rendering logic, per the Performance requirements.
7. **Multi-product catalogue PDF is ephemeral, like Module 15's CSV/Excel/Markdown exports** — base64 in the response, nothing persisted to storage or the DB. A PDF spanning many products doesn't belong to any single product's `ProductImage` rows, so inventing a new "artifact" table/model for it felt like overreach; reusing Module 15's exact "generate on demand, return as base64" precedent was the simpler, more consistent choice.
8. **A design *export* (single product or via batch-render) persists as a new `ProductImage` with `source_image_id=None`** — a rendered design is composed from potentially many layers/images, not derived from one single parent photo, so `ProductImage`'s existing single-parent lineage field genuinely doesn't apply (same as an `ORIGINAL` row's own null value). `variant_type` is chosen from the requested Output Preset via a small preset→variant map (reusing Module 20/21's already-modeled `TEMPLATE`/`INSTAGRAM`/`WHATSAPP`/`FACEBOOK` slots, falling back to the generic `TEMPLATE` bucket for presets with no dedicated slot) — same "fall back to a shared bucket" precedent `ai_enhancement_service.py`'s `ENHANCEMENT_OUTPUT_VARIANT` already established.

- **A new product is created for real the moment Step 1 is submitted**, not deferred to a final "Publish" click. ## 26. Product Studio White-Screen Investigation & Fix (2026-08-04)

**The brief**: every wizard step transition (Product Details → Upload Images → Studio → Templates → Preview → Publish) allegedly blanked the *entire application* — sidebar included — to white for 5-6 seconds. Explicit instructions: no new features, no backend redesign, no new APIs; find the real cause with measurements, not guesses, then fix only what's needed.

### Root cause — what the code actually does vs. what the bug report assumed
The bug report's own diagnostic questions (§instructions 1-3) assumed each step might be a separate Next.js route and asked whether React was unmounting/remounting the whole Studio. **Neither is true**: `src/app/admin/catalogue/studio/[productId]/page.tsx` is the only route; all 6 steps are `currentStep` states inside one `StudioProvider`/`StudioShell` pair (`_components/studio/StudioContext.tsx` + `StudioShell.tsx`). Steps 2 through 6 never call `router.push`/`replace` — confirmed by grepping the whole `admin/catalogue` tree. So "is it a route-per-step problem" — no, and that's good news, but it means the actual cause was elsewhere.

**Two real, code-verified bugs were found and fixed** (both in the one place a route change genuinely happens — Step 1's "Continue" for a *brand-new* product):
1. `StudioShell.tsx` had `if (!isNewProduct && loadingProduct) return <skeleton-only-jsx>` — this replaced the **entire return value**, including the back button, page header, and step indicator, not just the step content. The moment Step 1 creates a product, `router.replace()` swaps the URL's `productId` from `new` to the real id, `isNewProduct` flips to `false`, and `loadingProduct` goes `true` again while the product reloads — during which the whole shell (not just content) vanished. This is the one place in the codebase that actually matches "entire application goes blank," and it's now fixed: the back button/header/step-indicator render unconditionally; only the content slot below them swaps between a skeleton, an error state, and the active step.
2. That reload was also **redundant** — `catalogueService.createProduct()` already returns the full saved product, and Step 1 calls `setProduct(saved)` immediately before the URL change. The `useEffect` watching `[productId]` was unconditionally calling `reloadProduct()` again anyway, firing a second GET for data already in hand. Fixed with a ref-tracked check: if `product.id` already equals the new `productId`, skip the refetch entirely.

**Two general resilience fixes**, not tied to a specific bug but reducing per-visit backend load and re-render churn every other step is also subject to:
3. `Step4Templates.tsx` called `catalogueService.listTemplates()` in its own `useEffect` on every mount — since switching to a different step component is a real unmount/mount (different component identity, unavoidable in a step-array wizard like this one), *every single visit* to the Templates step re-fetched all 10 templates from scratch and showed nothing but a small skeleton block meanwhile. Templates are product-agnostic and static for the session, so they're now fetched once in `StudioProvider` and exposed via context (`templates`/`templatesLoading`); Step 4 just reads them.
4. `StudioContext`'s provider `value` was a fresh object literal on every render — any state change anywhere in the wizard (including a debounced preview finishing in the background on a step the user isn't even looking at) forced every context consumer to re-render. Wrapped in `useMemo`.

### What was measured, not estimated (backend, via curl, both dev servers already running)
Per-request timings against the real `localhost:8000` → live Supabase Postgres (`ap-northeast-1`), averaged over 3 runs each, tiny-payload endpoints:

## 27. Backend N+1 / Redundant-Query Optimization (2026-08-04)

**Scope, per explicit instruction**: backend query-count reduction only. No API contract changes, no request/response model changes, no business logic changes, no audit logging changes, no tenant isolation changes, `pool_pre_ping` left enabled, the create/update product post-commit re-fetch left alone. Everything below is a pure "same result, fewer round trips" change, verified by the full affected test suite passing unchanged (106/106) and by direct SQL-echo proof of the query counts before and after.

### Why `pool_pre_ping` and the create/update re-fetch were NOT touched (carried over from §26's investigation)
- **`pool_pre_ping`**: measured at ~450ms/request in isolation last session, but disabling it trades that for intermittent hard failures (`ConnectionDoesNotExistError`) — a failure class this exact project's test history has already hit (§5), made more likely here by the NAT64 network path this backend's DB traffic travels over (§26). Not safe to remove without a broader connection-liveness strategy, which wasn't requested.
- **`create_product`/`update_product`'s full re-fetch after commit**: the code's own comment explains this was already a deliberate fix for a real bug — a partial `db.refresh(product, attribute_names=[...])` left relationships expired, causing `MissingGreenlet` crashes on next access in this async ORM. Touching this needs its own targeted proof, which wasn't part of this pass's scope.
- **No `db.refresh()` calls were removed** — none of the four approved optimizations below required it, and per instruction, removing one requires first proving (via a targeted test) that the object already holds every server-generated field after commit. That proof wasn't done this session, so none were touched.

### What changed

1. **`_download_referenced_images` (catalogue_service.py)** — was a `for image_id in image_ids: await CatalogueRepository.get_image_by_id(...)` loop, one query per image referenced by a canvas (background/product/logo layers can each reference a different image). Now calls one new repository method, `CatalogueRepository.get_images_by_ids()` (`catalogue_repository.py`), which does a single `WHERE id IN (...)` query for every referenced image at once, then looks results up from a dict. Missing/foreign-tenant ids behave identically to before (silently absent → the existing "honest placeholder" path in `render_canvas()`, untouched).
2. **`_get_owned_products` (catalogue_service.py)** — was a `for product_id in product_ids: await CatalogueRepository.get_product_by_id(...)` loop (used by batch-render and the multi-product PDF). Now calls one new repository method, `CatalogueRepository.get_products_by_ids()`, one `WHERE id IN (...)` query for the whole batch. The exact original validation semantics are preserved deliberately: the code still iterates `product_ids` **in their original order** and raises `ResourceNotFoundException(f"Product ID '{product_id}' not found")` — the identical exception, identical message, identical "first missing id in list order" behavior — for any id not found in the batch result; duplicate ids in the input still produce duplicate entries in the output, exactly as the per-id loop did (SQLAlchemy's session identity map already deduped repeated primary-key fetches within one session, so this is a true no-op change in observable behavior).
3. **`upload_image` (catalogue_service.py)** — was fetching the product via `get_product_by_id` (which eager-loads `product.images` via `selectinload`), then, a few lines later, re-querying the *same* images again via a separate `get_images_by_product()` call to compute the next display order / primary flag. The second call is deleted; the code now filters the already-loaded `product.images` in memory. Same data — the eager-loaded collection reflects the DB state at the same point in the request the second query would have.
4. **`/health` (health.py)** — dropped the endpoint's own unused `db: AsyncSession = Depends(get_async_db)` parameter. `check_database_connection()` (unchanged) already opens its own session to run the ping; the endpoint was opening a second session it never used.

**New repository methods added** (both tenant-scoped, matching every existing method's isolation pattern exactly): `CatalogueRepository.get_images_by_ids()` and `CatalogueRepository.get_products_by_ids()`, in `catalogue_repository.py`.

### Proof of query-count reduction (SQL echo against the real, unmodified, post-edit app code — not inferred)

```
get_products_by_ids(db, [id1, id2], tenant_id)   → exactly 2 SQL statements total
                                                     (1 products SELECT + 1 selectinload images SELECT)
                                                     regardless of how many ids are passed
get_images_by_ids(db, [id1..id4], tenant_id)     → exactly 1 SQL statement total
                                                     regardless of how many ids are passed
```

| N products | OLD (per-id loop) avg | NEW (batched) avg | Reduction |
|---|---|---|---|
| 1 | 601ms | 568ms | ~0% (no batching benefit at N=1, as expected) |
| 2 | 886ms | 596ms | 33% |
| 5 | 1972ms | 610ms | **69%** — NEW stays flat regardless of N; OLD scales linearly |

This is the clearest evidence of the fix: `_get_owned_products` (batch-render, catalogue PDF) used to cost 2 round trips *per product in the batch*; it now costs 2 round trips total, no matter the batch size.

## 28. Product Studio UX & Performance Polish (2026-08-04)

**What was built**: replaced the 6-step wizard (Product Details → Upload Images → Studio → Templates → Preview → Publish, each a full-width stacked card that swapped via a `key`-driven remount) with one persistent Canva/Adobe-Express-style workspace: a fixed top header, a vertical left step nav with a progress bar, a large center canvas that is mounted exactly once and never remounts on a step change, and a right-hand panel that is the *only* thing that swaps per step. **Frontend only** — no new backend endpoints, no changed request/response shapes, no changed business logic, no dropped functionality. Every control from the old 6 steps still exists; only its container changed.

### Why this is a real "never disappears" guarantee, not just a visual claim
§26's investigation already established the wizard had no per-step routing — steps were always `currentStep` state, not routes. What §26 didn't fully solve was that **switching to a different step component is still a real unmount/remount** (Step2UploadImages and Step3Studio are different component types — React tears down and rebuilds regardless of any `key`), and each old step owned *and re-rendered* its own copy of the "live preview" card. So every step transition still tore down and rebuilt an entire preview UI, even after §26's fixes.

This module removes that mechanism structurally rather than patching around it: the preview now lives in exactly one component, `StudioCenterCanvas`, instantiated once by `StudioShell` and never conditionally unmounted for any step 0–5 (the only unmount branch left is the pre-existing initial-load/error state, which — per §26 — already only replaces the canvas+panel area, not the header or nav). Only `StudioRightPanel`'s *children* change per step, and that region was never claimed to be preview — it's tool controls, which are supposed to look different per tool, exactly like Canva's own right panel does.

### The actual "never blank" mechanism — `SmoothImage`
A plain `<img src={x}>` still blanks to nothing for a frame when `x` changes, while the browser fetches the new source — swapping *which* image the canvas shows (switching steps, switching selected image, a debounced preview arriving) would have re-introduced a smaller-scale version of the same problem `StudioCenterCanvas`'s persistence solves. `SmoothImage` (`_components/studio/SmoothImage.tsx`) fixes this at the image level: on a `src` change it preloads the new image off-screen via a real `new Image()` (this is the module's "image preloading" requirement, not a separate feature bolted on), and only swaps what's rendered once that preload's `onload` fires — so the previous frame stays on screen for the entire duration of the new one loading, then cross-fades in via a real CSS animation. `React.memo`'d since it's re-rendered on every debounced preview tick.

### Real CSS animations, not inert ones
`animate-in fade-in duration-200`-style classes were used throughout the old wizard (StudioShell, Collapsible, ImageViewer, Toast) but **never actually did anything** — they reference the `tailwindcss-animate` plugin, which `tailwind.config.js` has never had registered (`plugins: []`). Discovered while implementing this module's "smooth fade transitions" requirement and confirmed by grepping the whole repo for `tailwindcss-animate`/`@keyframes`/`fadeIn` — no matches anywhere. Added two small, dependency-free keyframes to `globals.css` (`.animate-fade-in`, `.animate-fade-in-up`) and fixed `Collapsible.tsx`'s one usage while touching it (in scope, isolated to Studio's own sections, zero risk to other consumers — confirmed via grep that Collapsible has no consumers outside `_components/studio/sections/`). `ImageViewer.tsx` and `Toast.tsx`'s own inert references were left as pre-existing, out-of-scope issues elsewhere in the codebase (not part of Product Studio).

### Architecture
- **`StudioContext.tsx`** — unchanged except `STUDIO_STEPS`'s labels (`Studio` → `Auto Fit` + `Image Processing` as two entries; `Preview`+`Publish` merged into one `Preview & Export` entry). Still 6 entries at the same indices, so `currentStep`/`furthestUnlockedStep`/`setCurrentStep` needed zero logic changes — this was a relabel, not a restructure, and reuses 100% of §25's state machine.
- **`_components/studio/workspace/`** (new) — `StudioTopHeader.tsx` (back button, inline-editable product name using the existing `updateProduct` call, Save/Preview/Export buttons — Preview and Export both jump to the Preview & Export panel rather than inventing new destinations), `StudioLeftNav.tsx` (vertical nav + progress bar, same lock/done/active logic the old horizontal pill row had), `StudioCenterCanvas.tsx` (the persistent canvas described above — also owns the Undo/Redo/Reset/Save-as-New-Version toolbar for Auto Fit/Image Processing and the Before/After grid for Preview & Export, since those are canvas-scoped actions, not tool-panel controls), `StudioRightPanel.tsx` (a switch on `currentStep` rendering one of the 6 panels below, the only component whose children remount per step).

Each is the old step's *controls* with its *preview* removed (preview moved to the canvas) — e.g. `TemplatesPanel` keeps the template-swatch grid but not the old "Selected Template — Real Render" card; `PreviewExportPanel` is old Step 5's actions (Step 5 itself had no controls beyond viewing, now in the canvas) plus all of old Step 6's Save Product/Save Version/Export Images/Generate PDF/Batch Render, unchanged, reorganized into `Collapsible` sections since the panel is narrower than the old full-width cards.

These were already self-contained (call `useStudio()` directly, take no props) from §25, which is exactly why splitting old Step 3 into two left-nav entries cost nothing beyond regrouping which sections render in which panel. One line changed: `AutoFitSection`'s own `Collapsible` gained `defaultOpen` — as one of 5 stacked sections it made sense collapsed by default; as the sole content of its own dedicated panel, landing on a collapsed single section would have looked broken.

### A real bug found and fixed via testing (not reasoned about in advance)
The first full test run produced 7 failures, all with the identical root cause:
```
sqlalchemy.exc.IntegrityError: insert or update on table "audit_logs" violates foreign key
constraint "audit_logs_tenant_id_fkey" — Key (tenant_id)=(tnt_...) is not present in table "tenants"
```
Every other `AuditRepository.create_log(tenant_id=...)` call site in this codebase passes an *already-committed* tenant id (`current_user.tenant_id`, from a tenant that was created in some earlier request). This module is the first place a **brand-new** `Tenant` and an `AuditLog` referencing that same brand-new tenant are ever inserted in the *same* flush. `AuditLog.tenant_id` is a bare `ForeignKey` column with no mapped ORM `relationship()` back to `Tenant` — so SQLAlchemy's unit-of-work has no object-graph edge to sort on, and the 4 batched `audit_logs` inserts (SQLAlchemy 2.0's `insertmanyvalues` batches same-mapper inserts together) could be flushed before the `tenants` insert. **Fixed with one explicit `await db.flush()`** immediately after all the `db.add()` calls and immediately before the audit-log-creation loop — this forces Tenant/Subscription/Branch/User to actually hit the DB (with real rows to reference) first, while staying inside the same uncommitted transaction, so the all-or-nothing rollback guarantee is unaffected. Confirmed via a full re-run: 7/7 previously-failing tests now pass.

### Transaction / rollback shape
Every uniqueness check is a read, run **before** any write is staged. This means a validation failure (duplicate subdomain, duplicate admin email, etc.) raises before a single `db.add()` call happens — nothing is ever partially created, by construction, not by relying on rollback machinery to clean up after a partial write. If something fails *after* writes are staged (e.g. a race-condition uniqueness collision at the DB level during the flush/commit itself), `get_async_db`'s existing exception handler (`except Exception: await session.rollback(); raise` — unchanged, the same handler every endpoint already relies on) rolls back the entire session, so no partial tenant is ever left behind either way. The onboarding email is sent **after** the commit, deliberately outside the transaction — an email delivery failure must never undo an already-successfully-provisioned tenant, the same resilience pattern `AuthService.forgot_password`/`request_email_verification`/`register_customer`'s signup hook already established.

### Security
- Temporary password: `secrets.choice`-based, 14 characters, bcrypt-hashed via the existing `hash_password` before storage — never stored in plaintext anywhere.
- **The temporary password is never emailed and never logged.** The onboarding email contains only the activation link — a deliberate design choice, not just a side effect: `ConsoleEmailProvider` (the active default until real SMTP is configured) logs the *entire* email body, so keeping the password out of the email body is what actually keeps it out of logs, not a separate redaction step. The password is returned exactly once, in the `POST /superadmin/tenants/provision` API response, for the SuperAdmin to copy if they need to share it directly.
- Activation token: real entropy (`secrets.token_urlsafe(32)`, Module 18's existing generator), hashed at rest, single-use (`used_at`), expires in 72 hours.
- Every write audit-logged; the provisioning SuperAdmin is always the recorded actor.

## 30. Product Studio — Professional Catalogue Pipeline (2026-08-04)

**What was built**: a quality-improvement pass on the Product Studio's existing local OpenCV + Pillow image pipeline — explicitly **not** a new feature and **not** any form of AI/online service (none was added, none was considered). The brief named four concrete quality problems with the current output; each was root-caused in the existing code before anything was changed, then fixed with classical, deterministic CV techniques only.

### Root-cause audit (done before any code was touched)
| Problem (as reported) | Root cause found in code | File |
|---|---|---|
| 1. "After preview... just places the product into a frame" | `_render_image_layer()`/`_fit_cover()` had zero template-composition awareness — every template used one hardcoded, product-agnostic box | `catalogue_render_service.py`, `catalogue_asset_library.py` |
| 2. "Background removal is inconsistent... too small... off-center" | `_build_grabcut_seed_mask()` unconditionally anchored a **fixed center 50%×50% block** as GrabCut's definite-foreground seed, regardless of where the actual product was | `image_processing_service.py` |
| 3. "Templates are just decorative borders... a necklace template should look like a necklace catalogue" | `_product_layer()` took one `margin_ratio=0.15` for every template — a ring and a necklace rendered into the literal same box | `catalogue_asset_library.py` |
| 4. "Large white flashes still appear... UX still feels slow" | `WatermarkSection` fetched the Media Library in its own local `useEffect`, re-fetching (with a fresh loading flash) every time its parent panel remounted on a step switch | `WatermarkSection.tsx` |

### Architecture changes

**1. GrabCut seeding — bbox-aware + connected-component refinement, not a fixed center block.**
`_build_grabcut_seed_mask()` no longer assumes the subject is centered and roughly half-frame. It now estimates *where the subject actually is* via the same color-distance thresholding `_detect_foreground_bbox` already used elsewhere in this file, refined to the **largest connected component** of "far from background" pixels (`cv2.connectedComponentsWithStats`) rather than a naive min/max bounding box over every such pixel. That refinement went through two iterations, the second one caught by this module's own quality measurements (not guessed correctly on the first try — see Tests below):
  - *First attempt*: reject the estimated bbox if it's under 1% of the frame (assumed too small = noise). Measurement caught this as a real regression: a small ring/stud shot in a wide frame can legitimately be under 1% of the canvas, and a percentage floor silently fell back to the old, inaccurate center-block seed for exactly that case — re-introducing Problem 2 for small products specifically.
  - *Fixed*: connected-component analysis instead of a naive bbox + percentage floor. This is what actually distinguishes a real (possibly tiny, possibly thin/hollow — a ring's band, a fine chain) product from scattered noise/reflection speckles: a min/max bbox over noise stretches across the whole frame, while a connected-component bbox only grows with an actually-contiguous shape. A density-based filter was considered and rejected for the same reason a percentage floor was: a hollow ring or thin chain legitimately fills well under half of its own bounding box, so density would misclassify real jewellery as noise.
  - The estimated bbox (once found) is shrunk 20% inward on each axis before being anchored as GrabCut's *definite* foreground — the bbox's own edges are the least reliable part of it (that's what GrabCut is being asked to refine), so anchoring safely inside avoids seeding definite-foreground on what might be background right at the boundary.
  - If no trustworthy bbox is found at all (very low-contrast product, or an already-tight crop), it falls back to the old fixed center-block behavior — preserved as a last resort, not removed.

**2. `AUTO_SCALE` default tuned**: `fill_ratio` default 0.8 → 0.85, matching the brief's "product should occupy approximately 80-90% of the canvas." Still fully overridable per-call; this only changes what happens when a caller doesn't specify one.

**3. Category-aware templates — real composition, not decorative overlays.**
`_product_layer()` gained an optional `box: (x_ratio, y_ratio, w_ratio, h_ratio)` parameter (ratios of the canvas, so the same composition works at any canvas size) alongside its original `margin_ratio` parameter. The 10 pre-existing general templates are **unchanged** — they still use the `margin_ratio` path — because `CatalogueDesign.template_key` is persisted as a historical label on saved designs (confirmed via `catalogue.py` model/schema inspection) and is never re-looked-up at render time, so removing or renaming any existing key would silently break old saved designs. All new work is additive.
  15 new category templates were added, each with a composition that actually suits that product's shape (not a copy of the general 70%-centered box):
  - **Necklace** ×4 (Luxury White, Premium Marble, Dark Luxury, Bridal) — portrait canvas (1080×1350), tall box (`0.10, 0.07, 0.80, 0.82`) so a hanging chain reads naturally.
  - **Ring** ×3 (Centered, Circular Balance, Luxury Black) — square canvas, small centered box (`0.32, 0.32, 0.36, 0.36`) with generous negative space; Circular Balance/Luxury Black add a new `CIRCLE_VIGNETTE` overlay (a thin centered double-ring accent) instead of a rectangular border on an inherently round subject.
  - **Earrings** ×2 (Balanced Spacing, Elegant) — wide box (`0.14, 0.16, 0.72, 0.68`) with generous side margins for a balanced left/right composition.
  - **Bracelet** ×2 (Horizontal, Luxury) — landscape canvas (1350×1080), wide horizontal band (`0.08, 0.30, 0.84, 0.40`) centered vertically.
  - **Pendant** ×2 (Portrait, Luxury) — portrait canvas like Necklace but a more compact box (`0.22, 0.15, 0.56, 0.55`), since a pendant alone is smaller.
  - **Bangle** ×2 (Circular Showcase, Premium) — square canvas with `CIRCLE_VIGNETTE`, same reasoning as Ring's circular templates.
  A new `TEMPLATE_CATEGORIES: Dict[str, str]` maps each of the 15 new keys to its category (`NECKLACE`/`RING`/`EARRINGS`/`BRACELET`/`PENDANT`/`BANGLE`); the 10 general templates deliberately have no entry (`category: null`). `TemplateSummary` gained a `category: Optional[str]` field, surfaced by `CatalogueService.list_templates()`.

**4. One-click, genuinely chained Auto Fit (frontend).**
`StudioContext` gained `applyEditOperations(ops[])` — the same upsert-by-type semantics as the existing single-op `applyEditOperation`, but for several operations in one state update and one debounced preview call. `AutoFitSection` now has a primary "One-Click Auto Fit" button that chains `REMOVE_EMPTY_SPACE(0.05)` → `AUTO_CENTER(0.05)` → `AUTO_SCALE(0.85)` through it — previously this required 3 separate user actions (2 button clicks + a slider drag), each firing its own debounced preview request. The individual controls remain for manual override.

**5. Media Library fetch-once (the real "unnecessary fetch" from Problem 4).**
`getMediaLibrary()` moved from a local `useEffect` inside `WatermarkSection` into `StudioContext`, mirroring the exact fetch-once pattern already established for Templates in Module 26. Before this, every time the user left and returned to the "Image Processing" step, `ImageProcessingPanel` (and `WatermarkSection` inside it) remounted — per `StudioRightPanel`'s step-switch — re-fetching the Media Library and showing a fresh loading skeleton, even though the data hadn't changed. Now it's fetched exactly once per session; `WatermarkSection` reads `mediaLibrary`/`mediaLibraryLoading` from context and calls the new `addToMediaLibrary()` to update it in place after an upload, instead of holding its own copy.

**6. Category-grouped Templates panel (frontend).**
`TemplatesPanel` now groups templates by `category`, with a "Suggested — {Category}" group (marked with a sparkle icon) pinned to the top when the product's free-text `category` field keyword-matches one of the 6 jewellery categories (`product.category` has no fixed enum on the backend — `String(100)`, nullable — so the match is a simple case-insensitive substring check, not an exact lookup). The extracted `TemplateTile` is `React.memo`'d with a **stable** `onSelect` reference (`StudioContext`'s `selectTemplate`, already `useCallback`-wrapped) rather than a fresh closure built in the parent's `.map()` on every render — passing a fresh closure per tile per render would have made the `React.memo` wrapper a no-op, since every tile's props would "change" on every parent re-render regardless.

### Post-completion fix: the actual cause of "After preview is worse than the original" (found via live testing, not this module's own audit)
The user tested the module in the real UI and reported the templated "After" image looking visibly *smaller/worse* than the un-templated "Before" — a real screenshot of the Preview & Export compare view showed a necklace filling most of the frame in "Before" and the same necklace, noticeably shrunk with a large empty margin, in "After." This module's original root-cause audit (table at the top of this section) diagnosed and fixed Problem 1 as a template-geometry problem (generic box → category-specific box) — correct, but **incomplete**: it missed a second, compounding cause that only became visible once a real Auto-Fit'd image was pushed all the way through a real template.

**Root cause**: `_render_image_layer()` (`catalogue_render_service.py`) passed the Product layer's source image into `_fit_cover()` as-is. `_fit_cover` is a correct cover-fit (fills its target box exactly, cropping overflow) — but it has no concept of "where the actual subject is within the source image." If the source already carries negative-space padding around the product — which `AUTO_SCALE(fill_ratio=0.85)` (Auto Fit) deliberately adds, on purpose, for the editor's own live-preview framing — `_fit_cover` treats that padding as real photo content and cover-fits the *whole padded canvas* into the template's product box. The product itself then ends up occupying only ~85% of that box instead of filling it, **compounding** with the box's own margin (e.g. a 70%-of-canvas box → product only ends up ~59% of canvas, not 70%). This is exactly the shrink the screenshot showed, and it explains why fixing the box geometry alone (this module's original fix) wasn't sufficient — the box was correct, but what got put inside it wasn't trimmed to the box's assumption that its input is "just the product."

**Fix**: `_render_image_layer()` now crops the source to its own tight foreground bounding box — reusing `_detect_foreground_bbox()` (`image_processing_service.py`, previously private to that file; now imported by `catalogue_render_service.py`, no circular import since neither file previously imported the other) — *before* handing it to `_fit_cover`. `_detect_foreground_bbox` already handles both transparent sources (alpha-based) and opaque sources (color-distance against an estimated backdrop, the same technique this module's own GrabCut seeding rewrite uses) — reused as-is, not reimplemented. A well-cropped source photo with near-zero existing padding is unaffected (the trim is a no-op); only sources that actually carry padding are affected, which is exactly the case that was broken.

**Measured, real before/after** (`verify_template_padding_fix.py` — a synthetic 800×800 source with a product occupying 85% of the shorter dimension, centered, rendered through the unmodified `LUXURY_WHITE` general template, whose product box is 70% of the 1080×1080 canvas):
| | Product linear coverage | Product area coverage |
|---|---|---|
| Before this fix | 59.4% × 59.4% | 35.3% of canvas |
| After this fix | **70.0% × 70.0%** (exactly the box) | **49.0% of canvas** (exactly the box) |

- Applies to **every** template (all 25 keys) and to Logo layers too, since both go through `_render_image_layer` — not a category-template-specific patch.
- **Tests**: `tests/services/test_catalogue_render_service.py` re-run after this change — **58/58 passed, 1.73s** (local, no network — this file's tests use synthetic in-memory images). Per explicit instruction to check only what's needed rather than the full suite again, the broader live-Supabase suites (`test_catalogue_service.py`, `test_catalogue.py`) were not re-run for this change, since it's confined to `_render_image_layer`, which only `test_catalogue_render_service.py` exercises directly.
- **Files changed**: `app/services/catalogue_render_service.py` only (+1 import, ~15 lines in `_render_image_layer`).

### Post-completion addition: Delete Product (found missing during live testing)
The Catalogue Studio product grid had no way to delete a product — reported directly by the user while testing this module. Investigation found the backend was already complete and safe: `DELETE /catalogue/products/{id}` (`CatalogueService.deactivate_product`) has existed since Module 20, is fully tested, soft-deletes via `is_active=False` (same convention as `Scheme`/`Branch`), and the frontend service method (`catalogueService.deactivateProduct`) already existed too — **it was simply never called from any component**. This was a frontend wiring gap, not a missing backend capability, so no backend/API/schema changes were needed.

**Added**: a Delete button (hover-revealed trash icon) on each product card in `src/app/admin/catalogue/page.tsx`, gated behind a confirmation dialog (reusing the exact `Dialog`/`DialogFooter` + `deleteTarget` state pattern already established for address deletion in `src/app/customer/addresses/page.tsx` — not a new pattern) and a toast on success/failure.

**What "delete" actually does** (disclosed accurately in the dialog copy itself, not just here): this is the existing soft-delete — the product is marked inactive (shown with the pre-existing "Inactive" badge, stays visible in the admin's own grid) and its images/design history are preserved, not erased. No customer-facing catalogue endpoint currently filters on `is_active` (grepped — none exists), so "customer-facing visibility" isn't a real distinction yet for this codebase; the practical effect today is admin-grid visibility only. Reactivation already works via the Product Studio's existing "Save" action (`StudioTopHeader.tsx`'s `handleSave` sets `isActive: true` as a side effect of saving) — reopening a deleted product and clicking Save restores it. A genuine hard/permanent delete was deliberately not built — it would irreversibly destroy image and design-version history with no undo, a materially different and riskier operation than what was asked for; flagged here rather than silently substituted.

**Files changed**: `src/app/admin/catalogue/page.tsx` only (new `deleteTarget`/`deleting`/`toast` state, `confirmDelete` handler, delete button, `Dialog` + `Toast` render). No backend files touched.
